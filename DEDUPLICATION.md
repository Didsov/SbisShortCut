# Дедупликация ККТ и метрики пропусков

## Где находился дефект

Дефект находился в `services.live_collector.collect_kkt_by_inn()`. Набор
`seen_reg_numbers` создавался до цикла аккаунтов и был общим для всего ИНН.
Если РНМ сначала встречался в аккаунте с неполной карточкой, повторная карточка
из следующего аккаунта не доходила до `KKT.Read`.

Последовательность дефекта:

1. `AccountContractor.List` возвращает аккаунты `9908993` и `4755172`.
2. В `9908993` встречается РНМ, но `KKT.Read` не возвращает срок ФН.
3. РНМ добавляется в общий `seen_reg_numbers`.
4. В `4755172` тот же РНМ содержит полноценную активную карточку.
5. Общий набор считает его дублем и пропускает до `KKT.Read`.
6. Первая карточка затем исключается в `find_all_kkt_by_owner_inn()` как
   `missing_fn_end_date`. В итоговой выдаче кассы нет.

Исправление: `seen_reg_numbers` создаётся внутри цикла каждого аккаунта.
Дубликаты удаляются только в пределах одного аккаунта, а один РНМ из разных
аккаунтов обязательно читается повторно.

## Остальные уровни дедупликации

### `services.registry.get_all_kkt_registry()`

Объединяет страницы Registry одного аккаунта. ККТ дедуплицируются по
`KKTRegId`, а при его отсутствии — по `AccountId + KKTId`. Этот уровень не
должен объединять данные разных аккаунтов: один вызов функции всегда относится
к одному `account_id`.

Проверять повторно при изменении пагинации или ключа Registry. Риск: две строки
одного аккаунта имеют одинаковый РНМ, но разные `KKTId` и различную полноту.

### `services.live_collector.collect_kkt_by_inn()`

Перед `KKT.Read` удаляет повторный РНМ только внутри текущего аккаунта. При
переходе к следующему аккаунту набор очищается.

Проверять при любом изменении области видимости `seen_reg_numbers` или порядка
обхода аккаунтов.

### `lookup.find_all_kkt_by_owner_inn()`

После загрузки всех аккаунтов объединяет полноценные карточки по РНМ. Карточка
без срока ФН исключается до финальной дедупликации. Если полноценные версии
есть в нескольких аккаунтах, предпочтение получает карточка с
`Действующая=True`, затем с более поздним сроком ФН.

Проверять при добавлении новых правил активности и обязательных полей.

## Метрики причин пропуска

`collect_kkt_by_inn()` возвращает:

- `skip_metrics` — агрегат по причинам;
- `skipped_items` — причина, `account_id` и РНМ;
- `account_statistics[].skipped_count` — количество пропусков аккаунта;
- `account_statistics[].skip_reasons` — причины внутри аккаунта.

Коды live-сбора:

| Код | Условие |
|---|---|
| `invalid_registry_item` | Registry вернул не словарь |
| `missing_kkt_id` | отсутствует `KKTId`; обычно папка или узел |
| `missing_reg_number` | есть `KKTId`, но отсутствует РНМ |
| `duplicate_in_account` | РНМ повторился внутри одного аккаунта |
| `foreign_owner` | ИНН карточки не совпал с запрошенным |
| `kkt_read_error` | `KKT.Read` завершился ошибкой |

Коды финальной фильтрации:

| Код | Условие |
|---|---|
| `parse_failed` | карточка не преобразована в `KKTInfo` |
| `missing_fn_end_date` | отсутствует срок ФН |
| `duplicate_complete_replaced` | прежняя версия РНМ заменена более качественной |
| `duplicate_complete_kept` | новая версия РНМ проиграла уже выбранной |

В журнал выводятся агрегаты:

```text
[CHECK_ACCOUNT] AccountId=... registry_kkt=... loaded_kkt=... skipped=... errors=...
[CHECK_SUMMARY] INN=... accounts=... loaded_kkt=... errors=... skip_metrics={...}
[FILTER_SUMMARY] INN=... raw_kkt=... selected=... skip_metrics={...}
```

Команда `/checkAcc ИНН` показывает те же счётчики по каждому аккаунту.

## Эталонный сценарий

Вводные:

```text
ИНН: 252100376720
РНМ: 0004306972061659

Аккаунт 9908993:
  карточка получена;
  FSEndDate отсутствует.

Аккаунт 4755172:
  тот же РНМ;
  FSEndDate = 2027-06-28.
```

Эталонное поведение:

1. `RegKKT.Registry` вызывается для обоих аккаунтов.
2. `KKT.Read` вызывается два раза для одного РНМ, по одному разу на аккаунт.
3. Версия из `9908993` учитывается в метрике `missing_fn_end_date`.
4. Версия из `4755172` попадает в итоговый результат.
5. Итоговая карточка содержит `account_id=4755172` и
   `fn_end_date=2027-06-28`.

Аналогичный эталон применяется к РНМ `0004814892009445` и
`0008198057009426`.

Регрессионный тест: `test_same_rnm_is_loaded_from_each_account`.
