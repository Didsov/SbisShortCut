# Правила обращения к внутренним JSON-RPC методам SBIS

Этот документ описывает формат запросов и ответов, фактически используемый
проектом `SbisShortCut`: JSON-RPC envelope, типизированные структуры `d/s`,
записи, наборы записей, ошибки и два обнаруженных варианта пагинации.

Это не документация публичного API SBIS. Внутренние методы, схемы, заголовки и
версии веб-клиента могут изменяться. Новый метод сначала нужно зафиксировать в
DevTools авторизованного браузера, а затем воспроизводить без Cookie, cursor и
других секретов в исходном коде или документации.

Запросы выполняются только с правами текущей авторизованной учетной записи.

## 1. Общий формат вызова

Внутренний RPC-вызов отправляется методом `POST`:

```json
{
  "jsonrpc": "2.0",
  "protocol": 7,
  "method": "Service.Method",
  "params": {},
  "id": 1
}
```

| Поле | Назначение |
|---|---|
| `jsonrpc` | Версия JSON-RPC envelope. В проекте используется `2.0`. |
| `protocol` | Версия внутреннего протокола сериализации SBIS. В проекте — `7`. |
| `method` | Полное имя RPC-метода, например `KKT.Read`. |
| `params` | Объект входных параметров конкретного метода. |
| `id` | Идентификатор вызова, который позволяет связать запрос и ответ. |

Имя метода должно совпадать сразу в трех местах:

```text
body.method
X-Calledmethod
Base64(X-Originalmethodname)
```

Пример для `KKT.Read`:

```http
X-Calledmethod: KKT.Read
X-Originalmethodname: S0tULlJlYWQ=
```

Base64 вычисляется от UTF-8 строки без перевода строки:

```python
import base64

method = "KKT.Read"
encoded = base64.b64encode(method.encode("utf-8")).decode("ascii")
```

## 2. Endpoint и версия

В проекте обнаружены два endpoint:

```text
https://online.sbis.ru/service/?x_version=<полная версия>
https://online.sbis.ru/billing_public/service/?x_version=<полная версия>
```

Выбор endpoint определяется методом, а не формой `params`. Например:

| Метод | Endpoint в проекте |
|---|---|
| `CRMClients.ListClientsOnline` | `/service/` |
| `BillingContractor.ReadCard` | `/service/` |
| `AccountContractor.List` | `/billing_public/service/` |
| `RegKKT.Registry` | `/billing_public/service/` |
| `KKT.Read` | `/billing_public/service/` |
| `License.AccountSummaryNewList` | `https://reg.tensor.ru/service/` |

`x_version`, `X-Saby-Appversion`, `X-Saby-Appid` и `X-Saby-Cfgid` следует брать
из одного актуального запроса веб-клиента. Нельзя автоматически считать, что
endpoint любого нового метода совпадает с endpoint уже известных методов.

## 3. Заголовки

Базовый набор, применяемый проектом:

```http
Accept: application/json, text/javascript, */*; q=0.01
Content-Type: application/json; charset=UTF-8
Cookie: <авторизованная сессия>
Origin: https://online.sbis.ru
Referer: https://online.sbis.ru/
X-Requested-With: XMLHttpRequest
X-Calledmethod: <Service.Method>
X-Originalmethodname: <Base64 имени метода>
X-Saby-Appid: <актуальный AppId>
X-Saby-Appversion: <актуальная версия приложения>
X-Saby-Cfgid: <актуальный CfgId>
```

Браузерные заголовки `sec-ch-ua*`, `sec-fetch-*`, `priority`, `accept-language`
и `user-agent` не являются частью бизнес-параметров метода. Добавлять их в
прикладной клиент следует только при подтвержденной необходимости.

Cookie хранится только вне Git, например в переменной окружения
`SBIS_COOKIES`. Нельзя печатать в лог весь запрос, если в нем присутствует
заголовок `Cookie`.

## 4. Типизированная запись `record`

SBIS передает запись как объект следующей формы:

```json
{
  "d": [123, "example", true, null],
  "s": [
    {"n": "Id", "t": "Число целое"},
    {"n": "Name", "t": "Строка"},
    {"n": "Active", "t": "Логическое"},
    {"n": "Parent", "t": "Запись"}
  ],
  "_type": "record",
  "f": 0
}
```

### Правило соответствия `d` и `s`

`d` содержит данные, `s` — схему. Соответствие строго позиционное:

```text
d[0] соответствует s[0].n  -> Id = 123
d[1] соответствует s[1].n  -> Name = "example"
d[2] соответствует s[2].n  -> Active = true
d[3] соответствует s[3].n  -> Parent = null
```

Основные правила:

1. Количество и порядок элементов `d` должны соответствовать `s`.
2. Нельзя удалить значение из `d`, оставив его описание в `s`.
3. Нельзя переставлять поля только в одном из массивов.
4. Отсутствующее значение обычно передается как `null`, если поле остается в
   схеме метода.
5. Вложенная запись снова оформляется как объект `record` со своими `d/s`.
6. Тип значения должен соответствовать `s[i].t`.

В проекте декодирование записи эквивалентно:

```python
decoded = {
    field["n"]: decode(value)
    for field, value in zip(record["s"], record["d"])
}
```

`zip()` молча отбросит лишние элементы более длинного массива. Поэтому перед
отправкой или разбором полезно отдельно проверять `len(d) == len(s)`.

### Поле `f`

В захваченных запросах встречаются `f: 0` и `f: 1`. Проект передает значение,
полученное из рабочего браузерного запроса, но не использует `f` для
декодирования. Нельзя считать его логическим флагом с универсально известным
назначением и менять без проверки конкретного метода.

## 5. Описание типов в `s`

Простые типы записываются строкой:

```json
[
  {"n": "INN", "t": "Строка"},
  {"n": "AccountId", "t": "Число целое"},
  {"n": "OnlyActive", "t": "Логическое"},
  {"n": "Position", "t": "Запись"},
  {"n": "FilterAddFields", "t": "JSON-объект"}
]
```

Массив описывается вложенным типом:

```json
{
  "n": "KindOf",
  "t": {
    "n": "Массив",
    "t": "Число целое"
  }
}
```

Другой пример:

```json
{
  "n": "DatePeriod",
  "t": {
    "n": "Массив",
    "t": "Дата и время"
  }
}
```

Типы и русские имена полей необходимо копировать точно. Не следует переводить
`Число целое`, `Логическое`, `Запись`, `Массив` или имя параметра на английский,
если метод ожидает русскую схему.

## 6. Набор записей `recordset`

Типичный ответ со списком имеет форму:

```json
{
  "result": {
    "_type": "recordset",
    "s": [
      {"n": "Id", "t": "Число целое"},
      {"n": "Name", "t": "Строка"}
    ],
    "d": [
      [1, "Первый"],
      [2, "Второй"]
    ],
    "n": false,
    "m": {}
  },
  "id": 1
}
```

Здесь:

- `s` — общая схема строк;
- каждый элемент `d` — строка значений по той же позиционной схеме;
- строка иногда сама может быть объектом `record`, который нужно декодировать
  рекурсивно;
- `n` в рассмотренных list/registry-ответах используется как признак наличия
  продолжения;
- `m` содержит метаданные ответа, в том числе возможную следующую позицию.

После декодирования приведенный пример выглядит так:

```json
[
  {"Id": 1, "Name": "Первый"},
  {"Id": 2, "Name": "Второй"}
]
```

Значения `n` и `m` относятся ко всему набору, поэтому их нужно прочитать из
сырого `result` до преобразования `recordset` в обычный список.

## 7. Формат успешного ответа

Минимальный успешный envelope:

```json
{
  "jsonrpc": "2.0",
  "result": {},
  "id": 1
}
```

`result` может быть:

- `record`;
- `recordset`;
- обычным JSON-объектом;
- массивом;
- скалярным значением;
- `null`, если метод не вернул данные.

Алгоритм обработки:

1. Проверить HTTP-статус.
2. Убедиться, что тело является JSON.
3. Проверить наличие `error` до обращения к `result`.
4. Сохранить сырой `result` для чтения `n/m`, если это список с пагинацией.
5. Рекурсивно декодировать `record` и `recordset`.
6. Проверить ожидаемый итоговый тип: словарь, список или скаляр.

## 8. Формат ошибки

Пример общей формы:

```json
{
  "jsonrpc": "2.0",
  "error": {
    "code": 0,
    "message": "Краткое сообщение",
    "details": "Подробности ошибки"
  },
  "id": 1
}
```

Не следует считать HTTP 200 признаком успешного RPC-вызова: SBIS может вернуть
JSON с ключом `error`. Текст выбирается в порядке:

```text
error.details -> error.message -> сериализованный error
```

В логах полезно сохранять безопасные данные:

- имя RPC-метода;
- HTTP-статус;
- `error.code`, `message`, `details`;
- номер попытки;
- безопасные идентификаторы объекта, если это допустимо политикой проекта.

Cookie, токены и полное тело с персональными данными логировать нельзя.

## 9. Пагинация по номеру страницы

Этот вариант используется методом `AccountContractor.List`:

```json
{
  "Навигация": {
    "d": [true, 100, 0],
    "s": [
      {"t": "Логическое", "n": "ЕстьЕще"},
      {"t": "Число целое", "n": "РазмерСтраницы"},
      {"t": "Число целое", "n": "Страница"}
    ],
    "_type": "record",
    "f": 0
  }
}
```

Порядок действий:

1. Начать со `Страница = 0`.
2. Отправить запрос.
3. Декодировать строки `result`.
4. Прочитать `has_more = bool(raw_result.get("n", false))`.
5. Если `has_more == false`, завершить обход.
6. Иначе увеличить `Страница` на единицу и повторить запрос.
7. Дедуплицировать результат по устойчивому идентификатору сущности.

Параметр `ЕстьЕще` во входной записи передается в форме рабочего браузерного
запроса. Решение о продолжении проект принимает по сырому `result.n` ответа.

Псевдокод:

```python
page = 0
all_rows = []

while True:
    response = call(page=page)
    raw_result = response.get("result")
    if not raw_result:
        break

    all_rows.extend(decode(raw_result))
    if not bool(raw_result.get("n", False)):
        break

    page += 1
```

## 10. Cursor/Position-пагинация

Этот вариант используется `RegKKT.Registry` и наблюдается в
`CRMClients.ListClientsOnline` и `License.AccountSummaryNewList`:

```json
{
  "Навигация": {
    "d": ["forward", true, 25, null],
    "s": [
      {"t": "Строка", "n": "Direction"},
      {"t": "Логическое", "n": "HasMore"},
      {"t": "Число целое", "n": "Limit"},
      {"t": "Запись", "n": "Position"}
    ],
    "_type": "record",
    "f": 0
  }
}
```

Первая страница всегда начинается с `Position = null`. Для следующей страницы
нужно передать позицию, возвращенную сервером, не разбирая и не конструируя ее
вручную без необходимости.

### Где находится следующая позиция

В подтвержденном ответе `RegKKT.Registry` она находится в метаданных
`result.m`. `m` само является типизированной записью:

```text
result.m.s -> найти индекс поля с n == "nextPosition"
result.m.d[index] -> recordset позиций
```

Внутри `nextPosition` проект находит строку с `id == null` — позицию корневого
списка — и берет соответствующее значение `nav_result`. Если `nav_result`
является JSON-строкой, она разбирается; полученный объект передается в следующий
запрос как `Навигация.Position`.

Конкретная внутренняя форма position зависит от метода. Например, CRM cursor
`CRMClients.ListClientsOnline` возвращается в
`result.m.nextPosition` как массив из одной непрозрачной строки. Для следующего
запроса строка упаковывается в `record` с единственным строковым полем `Cursor`,
`f: 1`, после чего запись передается как `Навигация.Position`. Передача cursor
без этой оболочки была проверена и приводит к RPC-ошибке.

Тип самого поля также зависит от метода: `RegKKT.Registry` объявляет `Position`
как `Запись`, а `License.AccountSummaryNewList` — как `Строка`. Значение и его
описание в `s` должны копироваться из контракта конкретного метода.

### Алгоритм cursor-пагинации

1. Установить `position = null`.
2. Выполнить вызов с текущей позицией.
3. Добавить новые строки, дедуплицируя их по ID сущности.
4. Прочитать `has_more` из сырого `result.n`.
5. Если `has_more == false`, завершить обход.
6. Извлечь `nextPosition` из метаданных именно этого ответа.
7. Если позиция отсутствует, не продолжать вслепую: зафиксировать частичный
   результат или признать короткую страницу окончанием только при подтвержденном
   для данного метода поведении.
8. Передать полученную позицию в следующий запрос.
9. Ограничить максимальное количество страниц.
10. Отслеживать повтор позиции и наличие новых уникальных строк.

Защита от бесконечного цикла:

```python
seen_positions = set()

while True:
    page = call(position=position)
    add_unique(page.items)

    if not page.has_more:
        break
    if page.next_position is None:
        raise PartialResultError("HasMore без следующей Position")

    key = canonical_json(page.next_position)
    if key in seen_positions and page.added_rows == 0:
        break

    seen_positions.add(key)
    position = page.next_position
```

Повтор `Position` не всегда означает ошибку: `RegKKT.Registry` может повторить
позицию, но вернуть новые строки. Поэтому завершать обход следует по сочетанию
повторной позиции и отсутствия прогресса.

## 11. Лимиты, повторы и частичные результаты

Рекомендуемые правила для списочных методов:

- устанавливать конечный `Limit`;
- ограничивать максимальное число страниц;
- дедуплицировать строки по устойчивому ID;
- при timeout повторять страницу, не меняя уже подтвержденную position;
- при систематическом timeout уменьшать `Limit`, если это проверено для метода;
- различать пустой полный ответ и частичный результат после ошибки;
- не начинать пагинацию заново после каждой сетевой ошибки;
- не повторять бизнес-ошибки, которые сервер вернул в JSON `error`;
- учитывать `Retry-After` для временных HTTP-ошибок.

Текущий HTTP-клиент считает временными статусы:

```text
408, 425, 429, 500, 502, 503, 504
```

Для Registry проект дополнительно уменьшает размер страницы при timeout и
возвращает накопленные строки как частичный результат при окончательном сбое.

## 12. Универсальный декодер `d/s`

Минимальный рекурсивный декодер:

```python
def decode(value):
    if isinstance(value, list):
        return [decode(item) for item in value]

    if not isinstance(value, dict):
        return value

    object_type = value.get("_type")

    if object_type == "record":
        schema = value.get("s") or []
        data = value.get("d") or []
        if len(schema) != len(data):
            raise ValueError("record: длина d не совпадает с длиной s")
        return {
            field["n"]: decode(item)
            for field, item in zip(schema, data)
        }

    if object_type == "recordset":
        schema = value.get("s") or []
        rows = value.get("d") or []
        result = []

        for row in rows:
            if isinstance(row, dict):
                result.append(decode(row))
                continue
            if not isinstance(row, list):
                result.append(decode(row))
                continue
            if len(row) != len(schema):
                raise ValueError("recordset row: длина d не совпадает с s")
            result.append({
                field["n"]: decode(item)
                for field, item in zip(schema, row)
            })

        return result

    return {key: decode(item) for key, item in value.items()}
```

Для диагностики полезно хранить отдельно:

```python
raw_result = response.get("result")
decoded_result = decode(raw_result)
has_more = bool(raw_result.get("n", False)) if isinstance(raw_result, dict) else False
metadata = raw_result.get("m") if isinstance(raw_result, dict) else None
```

## 13. Как подготовить входные данные для нового метода

Для любого нового RPC-метода:

1. Открыть нужный раздел в авторизованном браузере.
2. В DevTools выбрать фактический `POST` вызов метода.
3. Зафиксировать endpoint, `method`, `protocol`, актуальные Saby-заголовки и
   структуру `params`.
4. Удалить Cookie, session ID, device ID, персональные UUID и готовый cursor из
   сохраняемого примера.
5. Для каждой записи построить таблицу `индекс -> s[i].n -> s[i].t -> d[i]`.
6. Выделить обязательные идентификаторы, фильтры, сортировку и навигацию.
7. Для первой страницы заменить захваченный cursor на `null`.
8. Убирать поле только парой: значение из `d` и соответствующее описание из
   `s`. Если контракт метода неизвестен, безопаснее оставить поле и передать
   `null`, чем нарушить позиционную схему.
9. Выполнить тестовый read-only вызов на разрешенных данных.
10. Проверить форму `result`, `error`, `n`, `m` и последнюю страницу.
11. Добавить дедупликацию и ограничение числа страниц.
12. Проверить, что полученные объекты принадлежат выбранному клиенту/аккаунту.

## 14. Что нельзя считать универсальным

Следующие детали подтверждены только для рассмотренных методов и не должны
автоматически переноситься на любой другой сервис SBIS:

- значение `protocol = 7`;
- значение и назначение `f`;
- трактовка `result.n`;
- расположение `nextPosition` внутри `result.m`;
- структура cursor;
- допустимый максимальный `Limit`;
- возможность передать `null` вместо конкретного UI-фильтра;
- endpoint `/service/` или `/billing_public/service/`;
- набор обязательных заголовков;
- возможность повторить запрос без побочного эффекта.

Перед автоматизацией нового метода отдельно определить, является ли он
read-only. Методы изменения, удаления, отправки или оплаты нельзя повторять по
общей retry-схеме без проверки идемпотентности.
