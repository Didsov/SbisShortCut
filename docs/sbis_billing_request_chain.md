# Цепочка запросов SBIS: клиент, аккаунты и ККТ

Документ описывает фактические JSON-RPC-запросы, используемые проектом
`SbisShortCut`, а также запрос списка клиентов из раздела CRM.

Все вызовы выполняются в контексте уже авторизованной учетной записи SBIS.
Описанная цепочка не выполняет вход под клиентом и не расширяет права текущего
пользователя: сервер вернет только те данные, которые доступны его сессии.

## Общая схема

```text
Авторизованная Cookie-сессия SBIS
  |
  +-- CRMClients.ListClientsOnline
  |     `-- список доступных текущему пользователю клиентов
  |
  `-- BillingContractor.ReadCard(INN, KPP)
        `-- Billing ContractorId (@Лицо)
              `-- AccountContractor.List(ContractorId)
                    `-- AccountId[]
                          `-- RegKKT.Registry(AccountId)
                                `-- KKTId + KKTRegId
                                      `-- KKT.Read(AccountId, KKTId, KKTRegId)
```

Для поиска ККТ по известному ИНН запрос списка CRM-клиентов не требуется. Он
нужен, когда сначала требуется получить перечень клиентов, доступных текущей
учетной записи, а затем выбрать из него клиента и продолжить цепочку по его ИНН.

## Транспорт и авторизация

### Endpoint

В проекте используются два endpoint:

```text
https://online.sbis.ru/service/?x_version=<актуальная версия>
https://online.sbis.ru/billing_public/service/?x_version=<актуальная версия>
```

`BillingContractor.ReadCard` и `CRMClients.ListClientsOnline` отправляются на
`/service/`. Остальные запросы ККТ используют `/billing_public/service/`.

Версия должна соответствовать актуальному веб-клиенту. В приложенном запросе
использовалась версия `26.4234-220`, а в текущем коде проекта зафиксирована более
ранняя `26.3248-150.3`.

### JSON-RPC envelope

```json
{
  "jsonrpc": "2.0",
  "protocol": 7,
  "method": "Method.Name",
  "params": {},
  "id": 1
}
```

### Минимальный набор заголовков проекта

```http
Accept: application/json, text/javascript, */*; q=0.01
Content-Type: application/json; charset=UTF-8
Cookie: <SBIS_COOKIES>
Origin: https://online.sbis.ru
Referer: https://online.sbis.ru/
X-Requested-With: XMLHttpRequest
X-Calledmethod: <Method.Name>
X-Originalmethodname: <Base64 от Method.Name>
X-Saby-Appid: <актуальный AppId>
X-Saby-Appversion: <актуальная версия>
X-Saby-Cfgid: <актуальный CfgId>
```

`X-Originalmethodname` вычисляется динамически:

```python
base64.b64encode(method.encode("utf-8")).decode("ascii")
```

Из браузерного cURL удалены не относящиеся к бизнес-запросу заголовки
`accept-language`, `priority`, `sec-ch-ua*`, `sec-fetch-*`, `user-agent` и
`x-adaptive`. Cookie нельзя сохранять в документации, Git или логах.

## 1. Получение списка моих клиентов

### Назначение

Метод возвращает список CRM-клиентов, доступных авторизованному пользователю.

```text
POST https://online.sbis.ru/service/?x_version=<актуальная версия>
Method: CRMClients.ListClientsOnline
X-Originalmethodname: Q1JNQ2xpZW50cy5MaXN0Q2xpZW50c09ubGluZQ==
```

### Очищенный запрос первой страницы

SBIS использует типизированные записи: массив `d` содержит значения, а массив
`s` — описание полей в том же порядке. Поэтому удалять отдельный элемент только
из `d` или только из `s` нельзя. В шаблоне ниже сохранена форма захваченного
запроса, но убраны привязанные к состоянию интерфейса значения:

- период `2026-09-01` — `2026-09-30`;
- UUID закрепленной папки;
- cursor, указывавший на продолжение после клиента «Абсолют, ООО»;
- необязательные дополнительные поля карточек;
- фильтр `Conglomerate`;
- локальные значения раздела `.13..`;
- отдельный внутренний `Limit` фильтра.

| `Limit` | `null` | Внутренний лимит фильтра; фактический размер страницы задан в навигации. |
| `OptClientFilters` | `null` | Дополнительные предустановленные фильтры. |
| `PinFolders` | `null` | UUID закрепленных папок; персональное значение удалено. |
| `Region` | `null` | Регион клиента. |
| `Removed` | `null` | Фильтр удаленных записей. |
| `Requisites` | `[]` | Запрашиваемые/фильтруемые реквизиты. |
| `Responsible` | `null` | Ответственный сотрудник. |
| `Root` | `null` | Корень иерархии CRM; значение `.13..` удалено как контекстное. |
| `ShowFolders` | `["All"]` | Показывать общий набор папок без персонального `Pinned_uuid`. |
| `ShowOnly` | `Clients` | Возвращать клиентов, а не только папки. |
| `Sorting` | `Name` | Сортировать по названию. |
| `SortingOrder` | `ASC` | Сортировать по возрастанию. |
| `Tags` | `null` | Фильтр по тегам. |
| `ThemeData` | `null` | Контекст темы/представления интерфейса. |
| `WithoutFolder` | `false` | Не ограничивать выдачу клиентами без папки. |
| `Раздел` | `null` | Раздел CRM; `.13..` удален как контекстный. |
| `Reglament` | `null` | Фильтр по регламенту. |

### Пагинация списка клиентов

Первая страница отправляется с `Position: null`. Признак продолжения находится
в сыром `result.n`. Метаданные `result.m` имеют схему:

```text
ReadRows      Число целое
nextPosition JSON-объект
StopWord     Строка
mergeStrategy Строка
```

В подтвержденном ответе значение `nextPosition` — массив из одной непрозрачной
строки cursor. Для следующего запроса строку нужно завернуть в запись:

```json
{
  "d": ["<cursor из result.m.nextPosition[0]>"],
  "s": [
    {"t": "Строка", "n": "Cursor"}
  ],
  "_type": "record",
  "f": 1
}
```

Эта запись целиком передается как четвертое значение `Навигация.d`, то есть как
`Position`. Передача одной строки без оболочки `record` приводит к RPC-ошибке.
Cursor нельзя разбирать, изменять или повторно использовать с другим фильтром.

Полный проверочный обход с `Limit = 500` завершился штатно:

```text
страниц: 42
строк: 20874
уникальных ID: 20874
дубликатов ID: 0
строк с ИНН: 19866
строк с КПП: 6712
строк с @Лицо: 20874
последняя страница: result.n = false
```

Количество отражает состояние доступной CRM-выборки на 21 сентября 2026 года и
не является постоянным. Для сборщика важен вывод: не каждая строка содержит
ИНН, КПП ожидаемо заполнен лишь у части организаций, а `@Лицо` присутствовал во
всех проверенных строках. Строки без корректного ИНН нельзя передавать в
`BillingContractor.ReadCard`; их нужно пропускать с отдельной причиной.

### Подтвержденные поля ответа

Ответ является `recordset` из 50 полей. Для цепочки лицензий достаточно
следующего подмножества:

| Поле | Тип | Использование |
|---|---|---|
| `ID` | `Число целое` | Устойчивый ID строки для дедупликации CRM-выдачи. |
| `Name` / `Название` | `Строка` | Отображаемое название клиента. |
| `ИНН` | `Строка` | Вход для `BillingContractor.ReadCard`; обязательный для дальнейшей цепочки. |
| `КПП` | `Строка` | Необязательное уточнение поиска организации. |
| `@Лицо` | `Число целое` | Внутренний идентификатор лица CRM; не следует без проверки считать его Billing `ContractorId`. |
| `UUID` | `UUID` | UUID карточки клиента. |
| `ИдентификаторСПП` / `SppUuid` | число / UUID | Идентификаторы СПП. |
| `CountryCode` | `Строка` | Код страны для формирования реквизитов поиска. |
| `Type`, `Вид` | `Число целое` | Тип и вид записи. Значения являются серверными enum. |
| `ДатаЛиквидации` | `Дата` | Признак/дата ликвидации организации. |
| `НеОтображается` | `Логическое` | Признак скрытой записи. |

Остальные группы ответа:

- папки и иерархия: `@ПапкаКонтрагентов`, `FolderType`, `FolderUUID`,
  `ParFolderID`, `Lvl`, `CompositeKey`, `Раздел`;
- ответственные: `Responsible`, `Responsible.Name`, `Department`,
  `Department.Name`;
- адреса: `KLADR`, `ParsedAddressFact`, `ParsedAddress`,
  `АдресФактический`, `АдресЮридический`;
- регистрационные сведения: `РегНомерПФ`, `ОКПО`, `ОГРН`, `КодФилиала`,
  `HeadOrgID`;
- служебные признаки: `Раздел$`, `Раздел@`, `NotEmpty`, `SubType`, `IsOurOrg`,
  `cur_id`, `Order`, `GroupId`, `KeyType`, `SPPInfo`.

Для задачи сбора лицензий не нужно сохранять адреса, ФИО ответственных и другие
лишние персональные данные. Достаточно `ID`, названия, ИНН, КПП и технического
статуса обработки.

## 2. Поиск биллингового контрагента по ИНН

```text
POST https://online.sbis.ru/service/?x_version=<актуальная версия>
Method: BillingContractor.ReadCard
```

```json
{
  "Requisites": {
    "d": ["<INN>", null, "643", null],
    "s": [
      {"t": "Строка", "n": "INN"},
      {"t": "Строка", "n": "KPP"},
      {"t": "Строка", "n": "CountryCode"},
      {"t": "Число целое", "n": "BillingExtId"}
    ],
    "_type": "record",
    "f": 0
  }
}
```

| Поле | Назначение |
|---|---|
| `INN` | ИНН выбранного CRM-клиента. |
| `KPP` | КПП; допустим `null`, если он неизвестен или не нужен. |
| `CountryCode` | `643` — Россия. |
| `BillingExtId` | Внешний ID биллинга; для поиска по ИНН не задается. |

После декодирования ответа ключ `@Лицо` используется как `ContractorId`.

## 3. Получение аккаунтов клиента

```text
POST https://online.sbis.ru/billing_public/service/?x_version=<актуальная версия>
Method: AccountContractor.List
```

```json
{
  "Фильтр": {
    "d": [12345678, true],
    "s": [
      {"t": "Число целое", "n": "ContractorId"},
      {"t": "Логическое", "n": "OnlyActive"}
    ],
    "_type": "record",
    "f": 0
  },
  "Сортировка": null,
  "Навигация": {
    "d": [true, 100, 0],
    "s": [
      {"t": "Логическое", "n": "ЕстьЕще"},
      {"t": "Число целое", "n": "РазмерСтраницы"},
      {"t": "Число целое", "n": "Страница"}
    ],
    "_type": "record",
    "f": 0
  },
  "ДопПоля": ["AccountInfo", "TransportState"]
}
```

`12345678` заменяется на `ContractorId`. При `result.n == true` номер страницы
увеличивается. Из строк ответа используются `AccountId`, название аккаунта,
`AccountInfo` и `TransportState`. Следующие запросы выполняются для каждого
найденного `AccountId`, а не только для первого.

## 4. Получение реестра касс аккаунта

```text
POST https://online.sbis.ru/billing_public/service/?x_version=<актуальная версия>
Method: RegKKT.Registry
```

```json
{
  "Фильтр": {
    "d": [12345678, null, null, null, false, null, null],
    "s": [
      {"t": "Число целое", "n": "AccountId"},
      {"t": "Строка", "n": "OnlineOwnerId"},
      {"t": "Строка", "n": "folderUniqueId"},
      {"t": "Строка", "n": "hierarchyCompositeKey"},
      {"t": "Логическое", "n": "includeArchived"},
      {"t": "Строка", "n": "problemGroupId"},
      {"t": "Строка", "n": "status"}
    ],
    "_type": "record",
    "f": 0
  },
  "Сортировка": null,
  "Навигация": {
    "d": ["forward", true, 25, null],
    "s": [
      {"t": "Строка", "n": "Direction"},
      {"t": "Логическое", "n": "HasMore"},
      {"t": "Число целое", "n": "Limit"},
      {"t": "Запись", "n": "Position"}
    ],
    "_type": "record",
    "f": 0
  },
  "ДопПоля": []
}
```

| Поле | Назначение |
|---|---|
| `AccountId` | Текущий аккаунт из `AccountContractor.List`. |
| `includeArchived` | `false` — не включать архивные ККТ. |
| `Limit` | Размер страницы. Проект начинает с 25 и уменьшает его при timeout. |
| `Position` | `null` для первой страницы, затем позиция из метаданных ответа. |

Для каждой кассы сохраняются как минимум `KKTId` и `KKTRegId`. Строки без этих
идентификаторов нельзя передать в `KKT.Read`.

## 5. Получение полной карточки кассы

Полная схема, точные пути ФН/ОФД и правила определения состояния вынесены в
отдельный документ [`kkt_read.md`](kkt_read.md).

```text
POST https://online.sbis.ru/billing_public/service/?x_version=<актуальная версия>
Method: KKT.Read
```

```json
{
  "Params": {
    "d": [12345678, 987654, "0000000000000000"],
    "s": [
      {"t": "Число целое", "n": "AccountId"},
      {"t": "Число целое", "n": "KKTId"},
      {"t": "Строка", "n": "KKTRegId"}
    ],
    "_type": "record",
    "f": 0
  }
}
```

Все три значения берутся из текущего аккаунта и строки `RegKKT.Registry`.
Проект извлекает из ответа владельца, модель, заводской номер, РНМ, адрес точки,
срок ФН, номер и модель ФН, срок ОФД и версию ПО.

После чтения карточки необходимо сравнить ее ИНН с ИНН выбранного клиента. В
проекте касса отбрасывается, если `KKT.Read.ИНН` (или резервный `Registry.INN`)
не совпадает с исходным ИНН.

## 6. Получение сводки лицензий аккаунта

### Назначение

Метод вызывается из карточки контрагента и запрашивает лицензионную сводку для
конкретного биллингового аккаунта:

```text
POST https://reg.tensor.ru/service/?x_version=<актуальная версия>
Method: License.AccountSummaryNewList
X-Originalmethodname: TGljZW5zZS5BY2NvdW50U3VtbWFyeU5ld0xpc3Q=
```

Входной `AccountId` нужно брать из `AccountContractor.List` или из карточки
контрагента. Это идентификатор биллингового аккаунта, а не `ContractorId` и не
ИНН клиента.

### Очищенный запрос первой страницы

```json
{
  "jsonrpc": "2.0",
  "protocol": 7,
  "method": "License.AccountSummaryNewList",
  "params": {
    "Фильтр": {
      "d": [12345678, 2, false, false, ""],
      "s": [
        {"t": "Число целое", "n": "AccountId"},
        {"t": "Число целое", "n": "AccrualType"},
        {"t": "Логическое", "n": "NewAccrual"},
        {"t": "Логическое", "n": "OnlyAccrual"},
        {"t": "Строка", "n": "SearchString"}
      ],
      "_type": "record",
      "f": 0
    },
    "Сортировка": null,
    "Навигация": {
      "d": ["forward", true, 35, null],
      "s": [
        {"t": "Строка", "n": "Direction"},
        {"t": "Логическое", "n": "HasMore"},
        {"t": "Число целое", "n": "Limit"},
        {"t": "Строка", "n": "Position"}
      ],
      "_type": "record",
      "f": 0
    },
    "ДопПоля": []
  },

```

Число `12345678` является обезличенным примером. В рабочем коде его необходимо
заменить выбранным `AccountId` и не фиксировать в логике.

### Параметры

| Параметр | Значение первой страницы | Назначение |
|---|---:|---|
| `Фильтр.AccountId` | `<AccountId>` | Аккаунт, для которого запрашивается сводка лицензий. |
| `AccrualType` | `2` | Тип начислений. Точная расшифровка числового enum в ответе не передается и требует отдельного сравнения запросов интерфейса. |
| `NewAccrual` | `false` | Не ограничивать выдачу только новыми начислениями. |
| `OnlyAccrual` | `false` | Не ограничивать выдачу только начислениями. |
| `SearchString` | `""` | Пустая строка — без текстового поиска. |
| `Сортировка` | `null` | Явная сортировка не запрошена. |
| `Direction` | `forward` | Обход списка вперед. |
| `HasMore` | `true` | Входное значение навигационной записи из веб-клиента. |
| `Limit` | `35` | Максимальный размер страницы. |
| `Position` | `null` | Начало списка. На следующих страницах — позиция из ответа сервера. |
| `ДопПоля` | `[]` | Дополнительные поля не запрошены. |

В отличие от `RegKKT.Registry`, схема этого запроса объявляет `Position` типом
`Строка`, а не `Запись`. Следующую позицию нужно считать непрозрачной строкой и
передавать без самостоятельного изменения. Нельзя подставлять сюда объект
position из другого RPC-метода.

### Подтвержденный формат ответа

Успешный read-only вызов вернул HTTP 200 и `result._type = "recordset"`. В
проверенном аккаунте верхний recordset содержал одну строку и 41 поле,
`result.n = false`, то есть следующей страницы не было. Метаданные `result.m`
имели поля:

| Поле метаданных | Тип |
|---|---|
| `Masked` | `Логическое` |
| `CreateLead` | `Логическое` |
| `ShowContractor` | `Логическое` |
| `LicensesViewMode` | `Строка` |
| `nextPosition` | `JSON-объект` |

Основные группы полей верхней строки:

| Группа | Поля | Что содержит |
|---|---|---|
| Идентификация | `Id`, `AccountId`, `ComponentUUID` | Идентификаторы строки, аккаунта и компонента. |
| Назначение | `AssignmentTheme.Ids`, `AssignmentTheme.ReassignmentIds`, `CurrentAssign`, `IsMainAssignment` | Темы назначения и признаки текущего/основного назначения. |
| Состояние | `IsActive`, `State`, `ProlongationState`, `IsDemo`, `Masked` | Активность, состояния продления, демо-режим и маскирование. |
| Результат | `Result`, `ResultEditable`, `ResultPartial` | Вложенный результат обработки, возможность редактирования и частичность. |
| Ответственный | `Owner`, `ManagerId`, `DepartmentId` | Подразделение и сотрудник, отвечающий за аккаунт. |
| Представление | `Name`, `SecondName`, `Expandable` | Названия строки и возможность раскрыть детализацию. |
| Продление | `@AccountProlongations`, `Prolongation.ThemesCodes`, `Prolongation.Allowed`, `ProlongationsCounter`, `ProlongationsFromYear` | Связанные продления, разрешение и статистика продлений. |
| Сроки | `Dates`, `AutoPayment` | Вложенные сроки действия и дата автоплатежа. |
| Деньги | `PaidSum`, `TotalSum`, `BaseSum`, `Discount`, `DebtSum` | Оплаченная, итоговая, базовая суммы, скидка и долг. |
| Лицензии | `Licenses`, `Parameters` | Вложенные recordset лицензий и параметров. |
| Договоры и ККТ | `ContractId`, `DeltaCostContracts`, `KKT`, `WithCommonAccruals` | Связанные договоры, изменение стоимости и возможная связь с ККТ. |

`Dates` является вложенной записью со сроками и рассчитанными признаками:

```text
date_begin, date_end, DateBegin, DateEnd, FirstContractDateEnd, AssignmentDate
is_over, is_expiring, days_left, PercentLeft
Duration, DurationMonths, DurationName
text_until_date, text_contract_date, text_left_date, text_left_full
```

`Owner` содержит подразделение и сотрудника: идентификаторы, код и название
подразделения, ФИО, должность, город, даты закрытия/увольнения и UUID сотрудника.
Эти поля являются персональными и не должны целиком попадать в диагностический
лог.

### Вложенная структура `Licenses`

В проверенном ответе верхняя строка содержала одну группу `Licenses`:

| Поле | Назначение |
|---|---|
| `PaidSum`, `TotalSum`, `BaseSum`, `Discount`, `DebtSum` | Финансовая сводка группы лицензий. |
| `DateBegin`, `IsActive`, `IsDemo` | Начало действия и признаки активности/демо. |
| `Summary` | Краткая сводка по тарифу и количеству. |
| `Detailed` | Детализация по договорам. |
| `ContractIds`, `PreviewContractIds` | Связанные договоры. |
| `WithMainLicense`, `IsMainContractor` | Признаки основной лицензии и контрагента. |
| `Contractor` | Вложенная запись `INN`, `KPP`, `Id`, `Name`. |
| `Accruals`, `PartnerAccruals` | Начисления и партнерские начисления. |
| `ProlongationContracts` | Договоры продления. |
| `KKT` | Связанная информация о ККТ, если она присутствует. |

`Licenses.Summary` в проверенном ответе содержал одну строку:

```text
Name, Amount, ProlongationAmount, ExpirationDate,
ProlongationNomenclatures, Sum, DemoAccess, TariffType
```

`Licenses.Detailed` содержал три строки. Каждая строка связывает реестровую
позицию с договором и содержит:

```text
RegistryId, Id, Date, Contract, Contract.Status, Actions
```

Вложенный `Contract` содержит даты и срок договора, суммы, признаки оплаты,
счета и реализации, статус, автора, точку продаж, связанные услуги, начисления
и параметры. В `Contract.Services` находятся строки услуг со следующими
основными полями:

```text
Service.Code, Name, Amount, ShippedAmount, Shipped,
Sum, BaseSum, ShippedSum, TariffType, DemoAccess,
ExpirationDate, ProlongationAmount,
Accrual.StartDate, Accrual.EndDate, Accrual.Sum
```

Таким образом, метод возвращает не просто перечень лицензий, а иерархическую
сводку:

```text
аккаунт/назначение
  `-- группы лицензий
        |-- краткая тарифная сводка
        |-- договоры
        |     `-- услуги и начисления
        `-- продления и финансовые итоги
```

### Обработка ответа

Алгоритм разбора:

1. Проверить HTTP-статус и наличие JSON-RPC `error`.
2. Сохранить сырой `result` для чтения служебных `n` и `m`.
3. Если `result._type == "recordset"`, сопоставить каждое `result.d[row][i]`
   полю `result.s[i].n`.
4. Прочитать `result.n` как наблюдаемый признак продолжения списка.
5. При наличии продолжения извлечь следующую строку `Position` из метаданных
   ответа именно этого метода.
6. Дедуплицировать верхние строки по `Id`, договорную детализацию — по ее `Id`
   или `RegistryId`, услуги — по `ContractService.Id`.
7. Рекурсивно декодировать `Result`, `Owner`, `Dates`, `Licenses`, `Detailed`,
   `Contract` и `Services`, потому что это вложенные `record/recordset`.

### Статус живой проверки

Запрос успешно проверен 21 сентября 2026 года с локальной `SBIS_COOKIES`:

```text

result._type = recordset
верхних строк = 1
```

## Расширение на другие данные

Общий принцип разрешения идентификаторов:

```text
CRM-клиент -> INN/KPP -> ContractorId -> AccountId -> ID сущности -> Read/List
```

Для нового раздела нужно зафиксировать его запрос в DevTools, определить:

1. endpoint и имя RPC-метода;
2. входной идентификатор из предыдущего этапа;
3. соответствие элементов `d` описаниям из `s`;
4. схему пагинации и `Position`;
5. минимальные необходимые дополнительные поля;
6. проверку принадлежности результата выбранному клиенту.

В документацию и диагностические файлы нельзя переносить Cookie, токены,
идентификаторы сессии и персональные cursor/UUID, если они не являются частью
публичной схемы метода.
